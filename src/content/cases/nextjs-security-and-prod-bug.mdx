## The client's need

Results for a large network's customers were scattered across messages, email links and separate vendor platforms. The portal unifies them, reading in real time from a legacy system of record through an integration middleware layer, and **stores none of that data itself**. I am one of two full-stack developers, with a project manager, an architect and a cloud engineer.

## What I proposed

I designed and built all five product screens straight in React, skipping standalone mockups so the design is the implementation: login, a two-step registration with transactional validation, password recovery, profile, and a results dashboard with search and filters.

## The hard call

> QA reported two symptoms. I measured instead of guessing, and found one cause.

The system of record returns one row per version of a report, so a single result arrived up to nine times: **13 rows for 5 results**, and paginated records reappeared across pages. I fixed it on both sides: a ROW_NUMBER correction in the integration query, and deduplication with latest-version selection in our mapper. That user's payload dropped from **1,331 KB to 461 KB**. Along the way I disproved a suspected pagination bug in another system with probe data, instead of assuming it.

## Outcome

In development and deployed to QA. The codebase runs **842 tests green**, and a parallel review by two reviewers found 0 critical issues and 0 real bugs.
